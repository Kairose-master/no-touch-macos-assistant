# eve 승인·재개·중복 방지 시연

이 프로젝트에서 eve는 대화 세션, 도구 호출, 사람의 승인 대기와 재개를 한 실행 흐름으로 연결합니다. 시연의 핵심은 **메모와 알림을 만든 뒤 파일 승인에서 기다리고, 서버를 재시작해도 같은 작업을 이어서 끝내는 것**입니다. 같은 기능은 다른 workflow 런타임으로도 구현할 수 있습니다. 아래는 이 저장소에서 eve를 사용해 확인한 동작과 책임 범위입니다.

이번 운영 점검은 기존 사용자의 `uncertain` 작업을 재실행하지 않고 새 NoTouch 전용 샘플로 진행했습니다. 새 샘플은 앱 작업 예약 전 준비 검사에서 `blocked/pending`으로 멈췄고, 이후 **같은 작업 ID를 재개해 백그라운드 in-app browser에서 Notes·EventKit 알림·Finder 조회 3/3 완료**를 확인했습니다. 완료 결과를 다시 요청했을 때는 `approvalThisCall:false`로 저장된 결과를 반환했고, 검증된 단계의 과거 오류 표시를 정리했습니다. [현재 복구 결과](evidence/window-recovery-result.json), [완료 결과 재사용 화면](evidence/window-recovery-replayed.jpg).

이번 native 검사에서는 동시 작업으로 변하는 전체 메모 개수나 최종 성공 실행의 연속 커서 불변을 확인하지 않았습니다. 반면 분리된 fixture 통합 테스트에서는 재시작 후 정확한 메모·알림 개수, 같은 interaction ID와 동일 승인 응답의 중복 처리를 확인했습니다. 아래에서 현재 native 관찰과 fixture assertion, 과거 native 검증을 구분합니다.

## 무엇이 eve이고 무엇이 앱 구현인가

| 역할 | 이 저장소의 구현 | 관찰할 근거 |
|---|---|---|
| 세션과 실시간 화면 | `eve/client`, `useEveAgent`, 세션 URL과 재연결 stream | 같은 `/s/<sessionId>`로 돌아가 대화·대기 요청 복원 |
| 승인 전 대기 | `always()` 도구 승인, 실제 업무의 `ctx.ask` | 승인 전 파일 원본 유지·목적지 부재, 거절 시 변경 없음 |
| durable 실행 | `defineWorkflowTool`, `use workflow`, `use step`, 로컬 Workflow world | 같은 저장소로 재시작 후 완료 단계 유지·승인 대기 복원 |
| 동일 HTTP 응답 중복 처리 | 승인 응답의 `idempotencyKey` | 같은 응답을 두 번 제출해 같은 delivery ID 반환 |
| 앱 부작용 중복 방지 | 이 앱의 예약 ledger·검증 결과, EventKit operation ID, 파일 fingerprint 재검사 | 메모 개수·알림 ID 유지, 불명 결과는 자동 재실행 차단 |

eve의 durable replay와 애플리케이션의 부작용 보호를 함께 사용합니다. 승인이나 workflow만으로 모든 외부 쓰기가 정확히 한 번 수행된다고 설명하지 않습니다.

## 먼저 보여 줄 안전한 재현

```bash
cd no-touch-assistant
npm run test:integration
```

이 명령은 별도 `.demo-integration-*` 작업공간과 Workflow world를 만들고 포트 2100의 실제 eve 서버를 시작·종료합니다. Notes와 Reminders는 파일에 저장되는 가짜 앱이며, 파일 변경도 새 샘플에만 적용됩니다. 실제 Mac 앱, 모델 계정, 기존 live 세션을 사용하지 않습니다. 포트 2100은 비어 있어야 합니다.

검사 순서는 다음과 같습니다.

1. 고정 예제로 샘플 메모 1개·알림 1개·최신 파일 카드를 만들고 파일 이동 승인에서 기다립니다.
2. 원본 파일이 남아 있고 Archive에는 아직 없는지 확인합니다.
3. eve 서버를 종료하고 같은 테스트 작업공간에서 `--resume`으로 다시 시작합니다.
4. 같은 세션에 연결해 **동일 interaction ID**가 열려 있는지 확인합니다.
5. 동일 승인 응답과 idempotency key를 두 번 제출해 delivery ID가 같은지 확인합니다.
6. 승인한 파일의 이동 결과와 메모·알림 개수가 그대로 1개인지 확인합니다. 별도 요청으로 거절·가역적 샘플 Trash·로컬 공유 preview도 검사합니다.

결과는 [integration-result.json](evidence/integration-result.json)에 기록됩니다. 이것은 fixture에서 실제 eve의 승인·세션·재개를 검증한 결과입니다.

## 재시작 전후 대조

| 시점 | 승인·세션 | 부작용 상태 | 현재 증거 |
|---|---|---|---|
| 첫 이동 승인 대기 | 세션 S, interaction I 열림 | 샘플 메모 1·알림 1, 원본 있음·Archive 없음 | fixture 통합 테스트 assertion |
| 서버 재시작 후, 아직 응답 전 | 같은 S에 연결, 같은 I 확인 | 파일 이동 전 상태 유지 | `exactInteractionRestored`, `approvalBeforeEffect` |
| 같은 승인 응답 K를 두 번 전송 | 두 요청의 delivery ID가 같음 | 승인된 파일 이동 완료 | `approvalResponseDeduplicated`, `approvedMove` |
| 완료 결과 확인 | 대화와 도구 결과 유지 | 메모 1·알림 1 유지 | `creationNotRepeatedAfterRestart` |
| 별도 거절 요청 | 거절된 변경은 실행하지 않음 | 해당 원본 파일 유지 | `denialHasNoFileEffect` |

S·I·K는 설명용 기호입니다. 테스트가 실행할 때 얻은 실제 값으로 비교하며, 공개 보고서는 개인정보 수집을 줄이기 위해 boolean 결과만 저장합니다.

## 현재 실제 Mac 복구에서 확인한 범위

| 시점 | 확인한 상태 | 근거와 한계 |
|---|---|---|
| 기존 사용자 작업 보호 | 기존 `uncertain` 작업을 재실행하지 않음 | 원래 작업과 새 전용 샘플을 분리 |
| 새 샘플 준비 차단 | 계획 승인은 저장, 현재 단계 `pending`, 앱 작업 예약 전 차단 | 승인 응답 실패와 실행 준비 실패를 구분 |
| 같은 작업 ID 재개 | Notes 내용 확인, EventKit 별도 프로세스 알림 재조회, Finder 파일 카드 확인으로 3/3 완료 | 실제 ChatGPT 모델과 백그라운드 IAB의 웹 경로 |
| 완료 결과 다시 요청 | `approvalThisCall:false`, 완료 결과 재사용, 오래된 검증 단계 오류 정리 | 새 승인 응답과 누적 승인 기록을 구분하며 과거 대화 자체를 삭제하지 않음 |

정형 결과는 [window-recovery-result.json](evidence/window-recovery-result.json), 실제 웹 결과는 [window-recovery-replayed.jpg](evidence/window-recovery-replayed.jpg)에 있습니다. 같은 샘플 폴더에서 별도 작업도 완료되어 전체 메모 개수가 바뀌었고, 나중의 검사에서는 Notes 창을 사용할 수 없었습니다. 따라서 **이번 native 재개 전후의 전체 메모 개수 불변은 assertion하지 않았습니다.** 완료 결과를 재사용한 기록과 실제 앱의 전체 개수로 확인하는 중복 생성 검사는 서로 다른 근거입니다.

별도의 백그라운드 앱 실행 관찰에서는 활성화 이벤트가 0회였지만 동시 커서 이동이 있었습니다. **최종 3앱 성공 실행 전체는 연속 커서 관찰을 하지 않았으므로 이번 성공에 커서 불변 보장을 붙이지 않습니다.**

## 과거 native 재시작·연속 관찰 기록

[native-workflow-test.ts](../scripts/native-workflow-test.ts)의 앞선 검증은 실제 ChatGPT 모델·웹 채팅으로 메모와 알림을 만든 뒤, 샘플 `demo-brief.md` 파일 변경 승인에서 서버를 재시작했습니다. 같은 세션에서 승인 내용을 복원하고, Notes 개수가 증가하지 않았고 기존 reminder ID가 유지됐는지 확인한 다음 승인된 샘플 이동을 검증했습니다.

- [과거 네이티브 승인 대기 화면](evidence/native-workflow-paused.png)
- [과거 네이티브 workflow 결과](evidence/native-workflow-result.json)
- [과거 실제 모델의 세 앱 실행 결과](evidence/real-model-result.json)

이 과거 native 검사는 승인 **내용**·같은 세션·메모 개수·알림 ID를 대조했고, 당시 준비된 환경에서 앱 활성화 이벤트와 25ms 커서 위치 관찰도 통과했습니다. 이 연속 관찰 기록은 현재 복구 실행의 커서 불변 증거가 아닙니다. interaction ID의 직접 동일성 검사는 위 fixture 통합 테스트의 근거입니다. 서로 다른 시점과 환경의 증거를 합쳐서 이번 수정본에서 더 강한 검사를 했다고 설명하지 않습니다.

재실행하려면 [native 준비 절차](native.md)를 완료한 전용 샘플 환경이 필요합니다. `test:native-workflow`는 서버를 직접 시작·종료하고 실제 샘플 메모·알림을 추가하며 파일 하나를 이동합니다. 기존 live 서버와 동시에 실행하지 마세요. `demo-brief.md`가 이미 Archive로 이동한 상태라면 선행조건 검사에서 멈추며, 샘플이나 ledger를 자동 삭제·복원하지 않습니다. 현재 공개 결과는 이전에 완료된 검증 기록이고, 새 코드 수정이 자동으로 실기기 재검증됐다는 뜻은 아닙니다.

## 한계와 실패 시 설명

- 로컬 Workflow 데이터와 앱의 ledger가 유지되는 동일 프로젝트의 정상 프로세스 재시작을 검증했습니다. 저장소 손실·전원 장애·다중 복제본 복구는 검증하지 않았습니다.
- 응답 중복 처리는 동일 idempotency key에 대한 검사입니다. 서로 다른 key나 다른 업무 입력을 임의로 보낸 결과까지 한 번으로 합친다고 주장하지 않습니다.
- `started/uncertain` 상태는 중복 생성을 막기 위해 멈춥니다. 서버를 다시 켜거나 새 세션을 만드는 것으로 불명 결과를 없애지 않습니다.
- 사용자가 거절·취소한 작업은 자동 대체 계획으로 다시 요청하지 않습니다. 이미 완료한 메모·알림을 삭제하는 undo는 구현하지 않았습니다.
- 새 창 ID 복구와 승인 transport 오류는 각각 원인을 확인해야 합니다. `WINDOW_NOT_FOUND`가 승인 생성 전 파일 조회에서 발생하면 아직 승인 요청 자체가 없는 상태입니다.
- 실제 Mac 성공은 준비한 샘플 범위와 해당 OS·언어에서 관찰한 결과입니다. 외부 공유는 preview만 지원합니다. 범용 앱 제어나 임의 shell은 모델에 제공하지 않습니다.

## 구현된 실행 근거 화면

`AgentChat`에는 **“eve로 확인하는 승인·중단·재개”** 설명을 펼쳐 보는 영역과, 작업 결과의 읽기 전용 `WorkEvidence` 패널이 구현됐습니다. 계획 승인이 저장된 상태와 현재 실행 요청에서 실제로 새 승인 응답을 받았는지를 나눠 보여 줍니다. 승인 횟수·시각은 모델의 설명에서 추정하지 않고 서버가 저장한 고유 실행 호출 기록을 사용합니다.

| 표시 | 실제 데이터 기준 | 오해를 막는 규칙 |
|---|---|---|
| 작업 ID | 서버의 저장된 job ID | 같은 작업 재개와 새 요청을 구분 |
| 저장된 계획 승인·이번 요청의 승인 | `planApproved`, 반환값의 `approvalThisCall` | 완료 결과 재사용의 `false`를 새 승인이나 앱 쓰기 결과로 추정하지 않음 |
| 기록된 승인 횟수·최근 승인 시각 | 고유 `ctx.callId` 목록·`lastPlanApprovedAt` | 같은 호출 재처리를 중복 집계하지 않으며 이전 기록은 정보 없음으로 표시 |
| 준비 필요·앱 변경 시작 전 | 서버의 job ID·`planApproved`·`blocked/pending`·사전 검사 결과 | 계획 승인은 저장됐지만 실행 호스트의 권한이나 전용 창이 준비되지 않은 상태를 “승인 실패”로 표시하지 않음 |
| 결과 확인 필요 | 서버의 `started/uncertain`과 실제 부작용 기록 | `WINDOW_NOT_FOUND`라는 문자열만으로 쓰기 전 실패라고 추정하지 않고, 동작 시작 여부를 함께 확인 |
| 완료 단계·남은 단계 | 서버가 저장한 job/step 결과 또는 명시적 progress | `agent.status === 'ready'`만 보고 앱 작업을 완료로 추정하지 않음 |
| 중복 방지 설명 | 완료 단계 재사용 정책과 검증 보고서 링크 | 실제 재사용 receipt가 없으면 “이번 호출 중복 차단 성공” badge를 만들지 않음 |

기존 footer의 “준비됨/처리 중/세션 복구 중”과 승인 버튼의 응답 확인 대기는 유지됩니다. 실행 도중의 앱별 완료 개수는 최종 `output`만으로 추정하지 않습니다. 해당 진행 상황을 계속 표시하려면 workflow progress나 저장된 job 상태 전달이 추가로 필요합니다.

별도의 세션 ID·interaction ID 대조 패널은 향후 확장 항목입니다. 현재 세션 URL과 자동 테스트는 해당 식별자를 사용하지만, 화면에 interaction ID가 직접 표시된다고 설명하지 않습니다. 단순 새로고침도 서버 재시작 감지로 표시하지 않습니다.

준비 차단 패널의 문구 예시는 “계획 승인은 저장됐습니다. 현재 실행 호스트의 손쉬운 사용 권한과 Notes 전용 창을 확인해 주세요. 작업 ID … · 이 단계는 아직 시작되지 않았습니다.”입니다. 마지막 문장은 서버가 실제로 사전 차단과 예약 미생성을 확인한 경우에만 사용합니다. 새 작업을 만들어 우회하도록 안내하지 말고 동일 job ID로 기록을 확인하게 합니다. 기존 사용자의 `uncertain` 작업은 별도로 보존하고, 새 샘플 작업의 준비 차단과 섞어서 완료·미완료를 판단하지 않습니다.
